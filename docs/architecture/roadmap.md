# 架构与技术演进路线

每次升级都由实际学习问题驱动。到达一个阶段不代表要一次加齐该阶段列出的技术；进入前先写目标、替代方案和验证方法。

| 阶段 | 领域形态 | 重点 / 进入条件 |
| --- | --- | --- |
| 1 | 纯 Java 单体；少量内存数据 | OOP、异常、基础集合、测试和简单业务规则。当前阶段。 |
| 2 | 保持单体 | 深入集合、泛型、IO/NIO 和序列化；通过实验比较 API 与数据结构。 |
| 3 | 保持单体 | 线程、同步、原子变量、锁、线程池、异步和 JVM；用可重复实验描述边界。 |
| 4 | Spring 单体 | 在 Java 基础明确后对照手写对象协作，学习 IoC、DI、AOP、MVC、事务。使用适配 Java 17 的稳定版本。 |
| 5 | 单体 + 外部基础设施 | 先以关系数据持久化订单/商品，再根据问题引入 Redis 和一种 MQ；每项分别做 ADR。 |
| 6 | 具备分布式边界的单体/服务 | 通过 RPC、超时、重试、幂等、一致性等实验理解失败模型；暂不要求立即拆服务。 |
| 7 | 按边界拆分的服务 | 只有当部署、扩展或团队边界构成实际学习问题时，再引入 Gateway、注册配置中心、观测、集群和 Docker。 |
| 8 | 综合交易学习系统 | 结合用户、商品、订单、库存、支付、风控与通知，研究源码、架构权衡和性能。 |

## 服务拆分的候选边界

未来可能形成 `user-service`、`product-service`、`order-service`、`inventory-service`、`payment-service`、`risk-service`、`notification-service`、`gateway`、`common` 和 `infrastructure`。这些只是候选边界，不在当前阶段预建 Maven 模块或空服务。

建议演进顺序：先让单体内的领域代码有测试边界；数据库接入时记录持久化决策；再做进程内模块边界实验；最后通过明确的通信、故障和部署需求拆服务。避免把单体内部类直接复制成分布式服务。

## 数据库接入准备

当前领域对象不依赖数据库 API，也不把数据库字段注解放进模型。Stage 4/5 到来后，先提出查询、事务和持久化需求，再决定是否需要 Repository 接口以及 MySQL/MyBatis；详见 [`../database/README.md`](../database/README.md)。
